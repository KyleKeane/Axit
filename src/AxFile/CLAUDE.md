# AxFile, the window

The WinForms side of AxFile: one list with a folder's entries, a video area shown only while a video plays, a status bar, the bundle's notices. The pure code (the folder's entries, the media rules, the player seam, the operations, the settings) is `src/AxFile.Core`, with its own `CLAUDE.md`. The spec is `docs/axfile/SPEC.md` ("SPEC.md" below); the guide `docs/axfile/user-guide.md` is embedded by `AxFile.csproj` for Help → User guide; the manual test plan is `docs/axfile/nvda-test-plan.md`. The bundle rules are in the root `CLAUDE.md`.

## Commands

```
.\run-axfile.ps1 C:\Music\Dune    # build Axit and start AxFile on the folder (run.ps1 -App file); a file selects itself in its folder
.\run-axfile.ps1                  # the last folder opened
dotnet build Axit.sln
dotnet test tests/AxFile.Tests/AxFile.Tests.csproj
```

## Rules

1. Every control gets an `AccessibleName`; the list is named with its count alone, the folder being the title (AF-2.1); nothing speaks on a plain arrow key; a command's result is one announcement (AF-7), on the list, or on the notice while one shows. The player's "Playing <name>" when it moves on by itself is the one unprompted announcement, and a setting.
2. The folder reads and the operations never run on the UI thread: `Task.Run` for the reads, the rename and the new folder, a thread of its own for the shell's delete; the player's events come back on the UI thread through the `BeginInvoke` the window hands `MediaPlayer` at creation.
3. No second window (bundle AX-7.2): questions and errors are notices; the folder picker and File Explorer are the system's own windows; the video area is a panel inside the window.
4. Run the `accessibility-review` skill on a change here before committing, and check it with NVDA following the test plan.

## Gotchas already learned

- Enter in a `ListBox` reaches `ProcessCmdKey` as `Keys.Return`; handled there with a `_list.Focused` check, and returning true keeps the list from dinging. Backspace, Space, F2 and Delete are the same.
- A read that comes back after the user has moved on is dropped (`_reads`): a slow folder would otherwise overwrite a faster one chosen later.
- The video area's handle must exist before the engine is made (`_video.Handle` creates it, hidden or not); the engine needs it at creation and draws nothing in it for a sound file.
- The queue holds paths, not entries: the list may show another folder by the time a file ends. Since the pane (AF-9) it is `AxFile.Core.PlayQueue`, and the player never indexes a list of its own.
- An invisible docked control takes no space, so the pane is a bottom-docked list that is simply `Visible = false` until it has something to show; the docking order in `Controls.AddRange` puts it between the folder list and the video area.
- An array parameter of a COM interface method marshals as a SAFEARRAY by default (P/Invoke defaults to a C array): `GetUIObjectOf`'s list of item ids is `[MarshalAs(UnmanagedType.LPArray)]`, or the shell reads garbage and the process dies with an access violation, which the probe found.
- A `[ComImport]` interface that derives from another gets no vtable slots from it: `IContextMenu2` and `IContextMenu3` repeat `IContextMenu`'s three methods before their own. A cast of the object to the derived interface is the QueryInterface.
- The shell's menu is tracked after a `BeginInvoke`, so that the Item menu (a `ToolStripDropDown`) has closed and the list has the focus back; `TrackPopupMenuEx` wants its owner in the foreground. A `WM_KEYDOWN` of Down posted just before it selects the first item for the keyboard, as File Explorer's Shift+F10 does; otherwise a native popup opens with nothing selected and NVDA reads nothing until an arrow key.
- The rename box sets its selection before it takes the focus: a `TextBox` that gets the focus selects all its text unless a selection was set first. `EndRename` gives the focus back to the list before hiding the box, or WinForms picks the next control itself; the box's `Leave` cancels a rename, and `CancelRename` is a no-op once `_renaming` is null, so the commit path does not cancel itself.
- The keys of an open `ToolStripDropDown` go to the drop-down's `ProcessCmdKey` through WinForms' menu-mode message filter, never to the form's: a key that should work inside a menu is handled in the menu subclass (`ItemMenu`). The menu's `Click` runs after the drop-down has closed; what needs the focus back on the list (the rename box, the shell's popup) is still posted with `BeginInvoke` to be safe.
- The clipboard's file list is `DataFormats.FileDrop` (`CF_HDROP`); whether File Explorer cut or copied is the four-byte "Preferred DropEffect" format (2 means move), read back as a `MemoryStream`. After a move the clipboard is cleared, as File Explorer does.
- The shell's extensions run in this process while its menu is up; an exception from one is caught and reported, a crash in one is not ours to prevent, which is why the menu is behind one item (AF-D8).
- A menu bar item's drop-down is the one WinForms makes, never a hand-made one (AX-6.6; `MenuTests` in the bundle's tests scans the sources for `DropDown = new`). The bar's Item menu was an `ItemMenu`, a `ContextMenuStrip`, for Ctrl+I inside it (AF-4.10): a drop-down that is not auto-generated has its `OwnerItem` set to null by `ToolStripDropDownItem.OnDropDownClosed`, so WinForms' Escape handling (`ToolStripDropDown.SelectPreviousToolStrip`) finds no owner strip and never resets the bar's `MenuAutoExpand`; from then on Left and Right open the neighbours' menus instead of moving along the bar (the user: "jumps into the items"). The context menu keeps the subclass, since a context menu has no owner item. Menu mode cannot be entered by posted messages in an off-screen probe (`ToolStripManager.ProcessMenuKey` wants the window in the foreground), so the keyboard walk of the bar is a step of the test plan, not a test.
- The selection is marks of the window's own written into the item texts (", selected"), not `SelectionMode.MultiSimple` (AF-D9): the list box's multiple selection separates the caret from the selection, so everything "current" would need `LB_GETCARETINDEX` and `LB_SETCARETINDEX`, and what NVDA says on the toggle was unknown. Setting `_list.Items[i]` to a new text deletes and reinserts the native item and selects it again; whether NVDA reads it a second time after Space is a step of the test plan.
