# Review of 2026-10-23

A critical review of the five days of development from 2026-10-18 to 2026-10-22 (187 commits: AxGit, AxTerminal,
AxFile, AxMedia, AxPreview, AxStart, the window base, the command palette), asked for by the user with the question
whether the loose edges felt in daily use are hard problems or symptoms of a quality problem in the code. The whole
repository was read, area by area, against the bundle's own standards (plain code a smaller model can change with one
app's folders, spec and notes in context; one obvious way to do each thing; the spec changed with the code; nothing
spoken unprompted; the caret moved only on the user's command). What the review found was verified by reading the
code before anything was changed; section 3 lists what was fixed the same day, section 4 what is verified and open,
section 5 what should be written again from scratch and in what order. The practices that keep the repository
healthy for years are `longevity.md`.

## 1. The verdict

- **The pure code is in good shape.** Every `.Core` project and `Axit.Core` are small, tested against recorded
  fixtures or temporary folders, and commented with their gotchas; a smaller model can change any of them with the
  folder, the spec and the notes in context. Two exceptions, both in the console pipeline: `SessionModel.ApplyChrome`
  (143 lines, six out parameters, eight pieces of scan state) and `TerminalModel`'s prompt rows kept by row number,
  which is where three of AxTerminal's bugs came from.
- **The windows are where the loose edges are, for two reasons, neither of them a hard problem.** State spread over
  many flags that are written in one place and read in another (AxClaude's question flow: sixteen pieces of state
  and three timers; AxFile's selection: five representations; AxStart's foreground: three patches for one rule;
  AxGit's views: six fields), and the second console window copied from the first instead of shared (AxTerminal's
  window is AxClaude's with the names changed, about 600 lines twice, so that every fix to the pty bridge, the write
  queue, the recording, the find or the signals has to be made twice). Both are what fast accretion leaves behind,
  not what hard problems force.
- **The hard problems are done carefully and are written down.** ConPTY's lifecycle and its blocking stop, the chrome
  scan of Claude's live block, NVDA's reading after a key press and the holds it forces (250, 300, 400 ms), the EDIT
  control's caret under word wrap, the reading breaks, MFPlay's thread affinity, the shell's context menu and the
  Recycle Bin through COM, the hidden window's foreground rules, `RegisterHotKey`'s limits: each has its timers,
  its fixtures and its gotcha in a `CLAUDE.md`. Those deserve their complexity; the flags around them do not.
- **The documents had rotted in their status lines, not in their requirements.** Seven spec headers said "planned",
  "not yet built", "beta" or "first draft" about apps released and passed under NVDA; the bundle spec described
  itself as of 2.0.0; About named four apps of nine; AxStart was missing from nine places a new app needs. The
  requirements and decisions themselves were right where they were checked, with the exceptions listed in section 4.
- **The shipped program differed from the tested one in one way that mattered.** The executable runs with invariant
  globalization and the tests did not, so "cafe" found "Café" in the tests and not in the program (the palette,
  AxStart, AxFile's entries), and AxFile's guard against two names that read the same did not see an accent written
  as two characters. The tests run as the program does now.

## 4. Verified and open

Found by the review and checked against the code, not yet changed: each needs a decision, an NVDA check, or more
than a day. In the order they are worth doing.

### AxClaude

- **Two write pumps after a restart** (`MainForm.Input.cs`, `Later(delay, PumpWrites)` not cancelled by `StopClaude`):
  a restart while an answer is typed out, then any send, dequeues on two chains and halves the 60 ms pacing. Likely
  behind the dropped characters noted in SPEC.md §12. Fix: one pump timer in a field, or a generation counter. The
  same code in `TerminalForm.Input.cs`.
- **The trill and the background alert both sound** for a question when the window is in the background
  (`ShowInArea` plays `Sounds.Notice`, then `Signal` plays the alert); FR-7.3 says the alert replaces the chime.
- **A reply line finalized just before a question is never spoken**: speech is held 250 ms and dropped when a prompt
  row arrives, and `Arrivals` has already marked the line spoken (`MainForm.Model.cs`, `Arrivals.cs`). D33 means to
  drop the question's rows, not the reply.
- **The kept message sent with a second Enter has no exchange block** (`MainForm.Input.cs`, `SessionModel.Send`
  returning false while a prompt is pending): Claude's `you:` echo stays visible, `i` stops on it, `o` does not.
  FR-2.10 does not say so.
- **App-made answers signal like questions**: the draft review's "y" and the drafts list's Escape flash the taskbar
  and can say "Question closed" (`MainForm.Area.cs`, `AnswerDraftsList` writes Escape without stamping `_answerAt`).
- **A question is spoken after the user dismissed it** when Escape comes within the 300 ms before its announcement.
- **`GitExclude.Update` rewrites a CRLF exclude file as LF.** Low.
- **Noted stale**: `claude-screens.md` says `/feedback` was recorded with 2.1.302 while `SlashCommands.cs` marks it
  2.1.281; 2.1.307's AskUserQuestion screen is described in the notes with no fixture.

### AxTerminal and the console pipeline

- **The prompt rows are tracked by row number** (`TerminalModel`, `_promptStartRow`, `_promptRow`): a row captured in
  one frame is read in later frames after the screen has scrolled. Three consequences: an output line that starts
  with the shell's continuation text (`> hello` in Git Bash, `>> x` in PowerShell) vanishes as a continuation row; a
  two-line prompt at the bottom row loses its first row; any `>>`-prefixed line on the stale row during a long
  command vanishes. Section 5.5 is the rewrite.
- **The hold timer spins at 1 ms while text is selected and output is pending** (`TranscriptView.cs`, the interval
  clamp): the UI thread wakes at the timer floor doing nothing. One line.
- **`DetachRows` keeps the cells** (`Screen.cs`): after a program homes the cursor without erasing, a shorter rewrite
  of row 0 reads "newtextOLDTAIL" and the untouched rows come back as new lines; AxClaude hides those copies
  (`RepaintHidden`), AxTerminal has nothing. `Reset` (`ESC c`) clears rows without raising `Cleared`.
- **`PtyHost.Dispose` blocks the UI thread up to 4 s** on a restart or close while a command ignores the console
  closing (`ping -t`). Accepted in AxClaude's §7.4; a confirmed restart could terminate at once.
- **The spec's "no trace" (AT-3.4, AT-8.2) now holds for the status bar and Ctrl+Q**; Copy diagnostics copies the
  status text too and should be checked against it.

### AxFile

- **"Already pasting" drops the in-flight part silently**: a cut of three with one still moving pastes two and says

- **Restart after an update on This PC** passes "This PC" as a folder and the new window says it does not exist.
- **`GoToAction` announces before it moves the focus**, which can cut the notification; verify under NVDA.

  the spec's, the plan's line is older); AF-3.10 says the list is named This PC and it is named by its count, as
  AF-2.1 says.

## 5. What to write again from scratch, and in what order

Each is a few hours to a day, each needs the NVDA plan of its app rerun, and each should be one branch with the spec
changed first. The order is by what the user feels most, then by what the other rewrites build on.

### 5.1 One console window for AxClaude and AxTerminal

`TerminalForm` is `MainForm` with the names changed: the pty bridge with its inbox and quiet timer, the paced write
queue, the recording, the find and the export, the taskbar flash and the signals, the music, the Tab and F6 switch,
the bookmark toggle, the folder picker, the notice hooks and the font. About 600 lines twice; every bug of section 4
in that code (the two write pumps, the find notice's second `_findText`) exists twice. The shape: a `ConsoleForm`
in `Axit.Forms` under `AxitForm`, holding the view, the field, the control area, the status pair, the pty bridge,
the write queue, the recording, the find, the export, the signals and the music; `MainForm` keeps what is Claude's
(the question list, the drafts, the Claude menu, the session model's hooks) and `TerminalForm` what is the shell's
(the marks, the shell menu, the recent commands). In the same stroke `LineStore` takes what both models copy:
`Feed`, the decoder, the parser and the screen, `ToggleBookmark`, `VisibleBefore`, `Trim`, `NewScreen`. This is
the one change that makes the one-folder promise true for AxTerminal, whose notes send a reader to AxClaude's.

### 5.2 AxClaude's question and attention state as one record

Sixteen pieces of state describe "what Claude waits on and what the window did about it" (`_promptAnnounced`,
`_handledWait`, `_shownWait`, `_areaText`, `_answerAt`, `_screenKeyAt`, `_draftOpenedAt`, `_askedQuestion`,
`_settingKey`, `_lastCommand`, `_keptMessage`, `_bellPending`, `_heldSpeech`, the attention timer, the area's
control, the area's hold) and three timers, written in one partial file and read in three. Every AxClaude bug of
section 4 is a flag or a timer read in one place and written in another. The shape: one nullable record
`Shown(signature, kind, at, byUser)` in one field, one `_userActedAt` stamp (for `_answerAt`, `_screenKeyAt` and
`_draftOpenedAt`, whose readers take their maximum anyway), and one `OnFrameSettled()` that compares the wait
signature with what is shown and does exactly one of show, replace, close or announce; the drafts as a second small
record. The timing constants (400 ms settle, 250 ms speech hold, 300 ms focus settle, 1 s delayed focus, 3 s "the
user's doing") are right and stay; they move to one place. `ShowClaudeScreen`'s Enter decision table becomes a pure
`ScreenActions` in `AxClaude.Core`, tested. Also: `ConfirmClose`, `ShowClaudeNotFound`, `LocateClaude` and `Post`
leave `MainForm.Area.cs`, where they are not the control area's.

### 5.3 The notice and focus core of the window base

One rule: on the first open remember the focused control (fallback `FocusTarget`); a `_chaining` flag around a
button's action so that a nested `ShowNotice` neither recaptures nor re-notifies; restore on the final close when
the control is not disposed; delete `FocusToKeep` and the four hand-written copies of it; `OnNoticeOpened` stays
and AxClaude derives `KeepCaret` from "the control before was the transcript"; `Announce` non-virtual, raising on
the panel when open and on `AnnounceSource` otherwise, and the two overrides go. Five lines of rule in place of four
members that interact; this is the single place the "loose edges" keep coming from in every window. Then `AxitForm`
into partial files by section (notices, find, fonts, updates, palette), as `MainForm`, `FileForm` and
`TerminalForm` already are; `CheckForUpdates` sets its state first and chooses its notice once; the orphaned
summary over `TextFont` goes back to its method.

### 5.4 AxFile's operation runner and its selection

Five hand-written runners (`Paste`, `MoveIntoNewFolder`, `Delete`, `RunArchiveWork`, `UndoAction`) each repeat
Begin, the in-flight bookkeeping, the await, the `finally`, `FailAction` or `End`, the result shown and said; the
"still showing that folder?" check went into each today (`ShowResultAsync`). One `RunOperation(doing, busyPaths,
work, done, said, selectAfter)` removes about 150 lines and makes the next operation ten lines. The selection lives
in five places that must agree (`_selected`, the ", selected" suffix in the item texts, the Shift range's three
anchors and its line, the `Before` lists of the Selection lines, `SelectedEntries`); `_rangeLine = null` is written
in eight places. The shape: a pure `Marks` in `AxFile.Core` (a set of paths and an optional range anchor; `Toggle`,
`All`, `None`, `ToHere`, `Extend`, `Keep`, each returning the new set, the paths whose mark changed and the line
text), tested, and one `ApplyMarks(changed)` in the window. That makes the count and the acted-on set one thing.
Also: `FillPane` without the `Keep()` protocol, now that it keeps its rows (done today); `TryFolder` and `TryEntry`
in place of the double guards; `OpenWay` and `WayOf` deleted (an enum equal to `IsFolder` since the split).

### 5.5 AxTerminal's prompt rows by line identity

At the B mark take the lines from the A row to the cursor row by identity (the screen already binds rows to lines),
hide continuation rows once, in the frame after a send, as "the lines directly under the prompt line whose text
starts with the continuation prompt", and never read a row number after the frame ends; the three booleans
(`_commandSent`, `_readyRaised`, `HasMarks`) and `Running` become one state (`NoMarks`, `Idle`, `Running`) with the
pending code. Fixes the three bugs of section 4 at once. Honest note: marks arrive mid-frame while rows are still
being written, which is awkward in itself; the row numbers are the self-inflicted part.
